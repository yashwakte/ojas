# Staff device restriction

Staff accounts — anyone with the `admin` or `delivery` role — can only hold a session on **one
device at a time**. Customers are deliberately exempt; this exists to protect the accounts that
can see every order, every customer address and phone number.

The point of the feature is that **a leaked staff password is not enough to get in**. An attacker
who knows the password still needs either the victim's browser profile or access to their email
inbox.

## How a device becomes trusted

A "device" is a random 32-byte id generated by the server and handed to the browser in the
`ojas_device` cookie. That cookie is `HttpOnly`, so page scripts can't read it — an XSS bug can't
steal the thing that makes the device trusted. Only its SHA-256 hash is stored, as the `_id` of
the `staff_devices` collection.

There are three ways a device gets bound:

1. **First admin bootstrap.** `POST /api/auth/bootstrap-admin` binds the machine that calls it.
   That endpoint permanently disables itself once any admin exists, so there is never a window
   where an admin account exists with no device bound to it.
2. **Accepting an invite.** A new staff member opens the single-use link emailed to them and sets
   their password; the browser they open it on becomes their bound device in the same action.
   Opening a link sent to the account's own address proves the same thing an emailed code would,
   so there is no second approval step. See "Staff onboarding" below.
3. **Email approval.** Any other staff sign-in from an unrecognised browser is refused with
   `403 needsDeviceEnrollment`. The staff member requests a code (`POST /api/auth/device/send-otp`,
   which requires their correct password), then redeems it (`POST /api/auth/device/enroll`).

Because the cap is one device per person, **approving a new device replaces that person's old
one** and deletes their refresh tokens — so signing in somewhere new immediately signs their
previous device out.

A device id identifies a *browser*, not a person. Several staff sharing one computer are all
bound to the same id, each approving it once; the rows in `staff_devices` are one per
(user, device). Revoking one person's device leaves the others sharing it untouched.

## Staff onboarding

An admin creates the account from the dashboard with a name, email, phone and role — **no
password**. The account is stored dormant (`passwordHash` empty), which nothing can sign into,
and an invite link is emailed.

- `POST /api/auth/staff` — creates the dormant account and sends the invite
- `GET /api/auth/invite?token=` — preview, so the page can show whose account is being activated
- `POST /api/auth/accept-invite` — sets the password, binds the device, issues a session
- `POST /api/auth/staff/{userId}/invite` — resend, which invalidates the previous link

Invites are single-use and expire after 48 hours; a TTL index sweeps up ones nobody opened. An
account that has already been set up cannot be re-invited — otherwise an admin could quietly
re-issue a link and take over a live staff account.

The invite link points at `Frontend:BaseUrl`, which **must be set to the real site origin in
Production** or the emails will link to localhost. On Render that is an environment variable, so
it is spelled with a double underscore rather than a colon — environment variable names can't
contain `:`, and .NET maps `__` onto the config hierarchy separator:

```
Frontend__BaseUrl = https://ojas-atta.vercel.app
```

Same convention as the `Jwt__Key`, `MongoDb__ConnectionString` and `Turnstile__SecretKey`
variables already set there.

## Where it is enforced

Both of these matter; enforcing only the first would be nearly useless:

- **Login** — an unrecognised device never receives a session.
- **Refresh** — a refresh token records the device it was issued to, and refreshing checks both
  that the presented `ojas_device` cookie matches and that the device is still bound. Without
  this, a refresh token lifted from a staff session would keep minting access tokens on the
  attacker's machine for the remaining 30 days of its life.

## Recovering a lost or stolen device

**Normal path — an admin does it.** Admin dashboard → *Delivery Partners* tab → the staff
member's card → **Unbind device**. This ends their sessions immediately. They approve a new
device by email code on their next sign-in.

**Break-glass — the last admin has lost their device.** There is deliberately **no recovery code
and no backdoor endpoint**: anything that could unlock an admin account remotely could also be
phished. Recovery is a direct database edit, which requires Atlas access that only the project
owner has:

1. Sign in to MongoDB Atlas and open the production cluster.
2. *Browse Collections* → the Ojas database → the `staff_devices` collection.
3. Find the document whose `userId` matches the locked-out account's `_id` in `users`.
4. Delete that document.
5. That account's next sign-in will be refused with the device-approval step, and the email code
   binds whatever device they use. Their old refresh tokens are already invalid, since the
   device they were pinned to no longer exists.

Note the standing dependency this creates: **email delivery must be working in production.**
With a cap of one device, the email code is the only self-service way back in. If Brevo is
misconfigured, the Atlas edit above is the only remaining path.

## Configuration

Device restriction itself has no keys or feature flags — it is unconditionally on for staff roles
in every environment. Two settings do matter:

- **`Frontend:BaseUrl`** — where invite links point. Wrong value means unusable invite emails.
  As an environment variable this is `Frontend__BaseUrl`.
- **`Email:SendInDevelopment`** — outside Production, OTP and invite mail is logged rather than
  sent, since the code and invite token both come back in the response body anyway. Set this to
  `true` only when testing real deliverability.

Outside Production the enrollment, reset and invite endpoints also return the code or token in the
response (`devCode` / `devInviteToken`) so the flows can be walked locally without a working
inbox. `AuthController` never populates those fields once `IWebHostEnvironment.IsProduction()` is
true.
